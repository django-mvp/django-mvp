{% extends "list_view.html" %} {% load i18n %} {% comment %} Overrides the outer `content` block, not page.header/page.content-wrapper. Those two sit inside page_view.html's , a plain block div between and that breaks the flex chain the height depends on — from there the filled layout cannot be built at all (specs/027-table-layout-and-column-styling/research.md R5). This view writes its own markup instead: the container and the two toolbars are bypassed, not reused. All six block names page_view.html declares are re-declared below, in positions that make sense for this layout, so a project overriding any of them on a table view keeps working. page.header uses {{ block.super }} to keep the default breadcrumbs; page.actions does not, because its default (list_view.html's search/sort/filter/create) includes sort, which a table view's own action set must not (FR-007) — see MVPTableViewMixin.actions. All three bars are plain flex rows rather than . A toolbar sizes each of its slots to their content, which is right when it holds a heading and a button group but wrong here: the bars have to span the table's full width to put the actions and the pagination at the trailing edge. page_view.html never puts inside a toolbar either. The breadcrumb row is a plain row for a second reason. renders {{ actions }} in its trailing slot, and a Cotton slot falls through to the context variable of the same name when the caller fills no slot — so any page whose context carries an `actions` key prints its repr there. The context key is `table_actions` now, but the bare row keeps the trap shut whatever a project puts in its own context. {% endcomment %} {% block content %}
